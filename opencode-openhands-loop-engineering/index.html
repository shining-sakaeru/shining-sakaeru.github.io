[OpenHands 실전 7화] OpenCode와 OpenHands로 Loop Engineering 만들기

빠른 OpenCode와 통합 검증에 강한 OpenHands를 Git, CI, 인수 기준으로 연결해 복사·붙여넣기 없는 개발 피드백 루프를 설계합니다.

Noah Sim

17 Oct 2026 — 6 min read
Share

OpenCode를 사용하면서 가장 먼저 느낀 점은 속도였습니다. 파일을 빠르게 읽고 고치며 짧은 피드백을 반복하기 좋았습니다. 반면 OpenHands는 컨테이너, 브라우저, GitHub, 외부 서버까지 확인하는 과정이 있어 상대적으로 느리게 느껴졌습니다. 그렇다면 빠른 OpenCode만 사용하면 될까요?

결론부터 말하면 도구를 V-모델의 왼쪽과 오른쪽으로 단순하게 나누기보다, OpenCode는 빠른 구현자, OpenHands는 독립 통합 검증자, CI는 반복 가능한 판정기로 두는 구성이 현실적입니다.

1. 속도와 정확도는 같은 축이 아니다

같은 LLM을 사용한다면 순수한 코드 생성 능력의 차이는 생각보다 작을 수 있습니다. 체감 속도는 파일 탐색, 안전 확인, 도구 실행, 환경 준비, 브라우저 검증 같은 오버헤드에 크게 좌우됩니다.

하지만 최종 작업 정확도는 코드 생성만으로 결정되지 않습니다.

작업 완료 품질
= 모델과 프롬프트
+ 올바른 컨텍스트
+ 테스트
+ 환경 재현성
+ 실패 복구
+ 독립 검증

OpenCode도 터미널과 테스트를 사용할 수 있고 OpenHands도 구현을 할 수 있습니다. “OpenCode는 코딩만, OpenHands는 테스트만”이라는 구분은 실제 기능보다 좁습니다.

2. V-사이클에서 중요한 것은 추적성

V-모델의 핵심은 특정 도구를 좌우에 놓는 것이 아니라 왼쪽의 요구사항과 오른쪽의 검증을 연결하는 것입니다.

요구사항대응 검증
Ghost가 OpenHands 재생성과 무관해야 한다OpenHands 재시작 후 Ghost HTTP 200 확인
컨테이너 장애 후 복구되어야 한다Ghost restart 후 healthcheck 확인
새 글이 정적 사이트에 포함되어야 한다sitemap과 export slug 비교
썸네일이 깨지지 않아야 한다src/srcset 이미지 URL의 HTTP 상태 검사
콘텐츠 원본은 하나여야 한다DB mount와 API 쓰기 경로 확인

OpenCode가 코드를 만든 뒤 테스트 없이 OpenHands에 넘기는 방식은 피드백을 늦춥니다. OpenCode도 자신이 만든 변경에 대한 단위 테스트와 로컬 통합 테스트를 실행해야 합니다. OpenHands는 그 결과를 그대로 믿지 않고 별도 환경에서 다시 검증합니다.

3. 공유 볼륨보다 Git을 경계로 사용한다

두 에이전트가 같은 작업 디렉터리를 동시에 수정하면 누가 어떤 변경을 만들었는지 불명확해집니다. 검증 중 원본이 바뀌고 충돌도 생깁니다.

코드는 Git을 Single Source of Truth로 두는 편이 안전합니다.

OpenCode 작업 브랜치
    ↓ commit / push
GitHub Pull Request
    ↓
CI 자동 테스트
    ↓
OpenHands 독립 검증
    ↓
사람 승인 후 merge

OpenHands는 동일 커밋 SHA를 별도 워크트리나 컨테이너에서 검증할 수 있습니다. 실패를 수정해야 한다면 원래 브랜치에 몰래 덮어쓰기보다 별도 커밋이나 수정 PR을 만드는 편이 추적하기 쉽습니다.

4. 무엇을 자동화하고 무엇을 에이전트에게 맡길까?

결과가 결정적인 작업은 LLM보다 일반 스크립트와 CI에 맡기는 것이 좋습니다.

  • lint와 formatter
  • 단위·통합 테스트 실행
  • docker compose config 검증
  • HTTP healthcheck
  • 정적 HTML의 깨진 링크와 이미지 검사
  • 빌드 산출물 생성 여부 확인

반면 로그 여러 개를 함께 해석하거나, 화면이 요구사항과 맞는지 판단하거나, 실패 원인을 추론해 수정안을 만드는 일에는 에이전트가 유용합니다.

결정적 검사 → CI와 스크립트
빠른 구현 → OpenCode
복잡한 판단·통합 검증 → OpenHands
최종 승인 → 사람

5. 현실적인 자동 피드백 루프

  1. 요구사항과 인수 기준을 issue 또는 문서로 작성합니다.
  2. OpenCode가 브랜치에서 구현하고 관련 테스트를 추가합니다.
  3. OpenCode가 로컬 테스트를 통과시킨 뒤 commit과 PR을 만듭니다.
  4. CI가 lint, unit, integration, build를 실행합니다.
  5. CI가 통과하면 OpenHands가 Docker·브라우저·Oracle Ghost·GitHub Pages 통합을 검증합니다.
  6. 실패하면 OpenHands는 근거와 재현 절차를 남기고, 필요하면 별도 수정 브랜치를 만듭니다.
  7. 사람이 diff와 인수 결과를 승인한 뒤 merge·deploy합니다.
  8. 배포 후 smoke test가 실제 URL을 확인합니다.

6. 처음부터 완전 자동 수정을 피하는 이유

테스트가 실패할 때 에이전트가 코드를 고치고 곧바로 운영에 배포하는 구조는 매력적이지만 위험합니다. 잘못된 테스트에 코드를 맞추거나, 수정 범위가 예상보다 커지거나, 인증·DB·인프라 변경이 자동으로 반영될 수 있습니다.

처음에는 자동 검증과 실패 보고까지만 연결하고, 익숙해진 뒤 저위험 작업부터 자동 수정 PR을 허용하는 것이 좋습니다. 문서나 포맷 변경과 달리 DB 마이그레이션, 인증, 운영 배포에는 사람 승인을 유지해야 합니다.

7. 내 환경에 맞춘 역할 분담

도구주 역할
OpenCode빠른 구현, 리팩터링, 테스트 작성, 로컬 반복
CI/CD매 커밋의 결정적·재현 가능한 검사
OpenHands독립 리뷰, Docker·브라우저·외부 서비스 통합 검증
Oracle Ghost블로그 콘텐츠의 단일 원본
GitHub Pages검증된 정적 공개 사이트

8. 오늘의 결론

빠른 도구와 강한 도구 중 하나만 선택할 필요는 없습니다. 중요한 것은 복사·붙여넣기로 결과를 옮기는 것이 아니라 Git 커밋, CI 결과, 명확한 인수 기준으로 두 환경을 연결하는 것입니다.

OpenCode가 빠르게 만들고, CI가 기계적으로 검사하고, OpenHands가 실제 통합 환경에서 다시 확인하며, 사람이 최종 위험을 승인하는 구조. 이것이 현재 환경에서 구현 가능한 Loop Engineering의 출발점입니다.
