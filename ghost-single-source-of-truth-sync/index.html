[OpenHands 실전 6화] Ghost DB 동기화보다 중요한 단일 원본 설계

OpenHands와 Oracle Ghost의 SQLite 복사본이 어긋날 수 있는 이유를 살펴보고, Admin API와 sitemap을 중심으로 단일 원본을 설계합니다.

Noah Sim

14 Oct 2026 — 5 min read
Share

Ghost를 별도 Docker 컨테이너로 분리한 뒤에는 서비스가 안정적으로 살아났습니다. 하지만 곧 더 중요한 문제가 보였습니다. OpenHands 작업공간에도 ghost-local.db가 있고 Oracle Ghost 컨테이너도 SQLite DB를 사용하고 있었습니다. 두 파일의 현재 내용이 같더라도 앞으로 계속 같은 상태를 유지한다는 보장은 없습니다.

1. 같은 내용과 같은 파일은 다르다

OpenHands 로컬 DB의 공개 글 23개를 Oracle Ghost의 공개 URL과 대조했을 때 누락, 제목 불일치, 대표 이미지 누락은 모두 0건이었습니다. 현재 콘텐츠는 일치한 셈입니다. 그러나 이것만으로 두 서비스가 같은 DB 파일을 실시간 공유한다고 결론 내릴 수는 없습니다.

파일 해시가 같아도 과거 어느 시점에 복사한 별도 파일일 수 있습니다. 정말 같은 원본인지 확인하려면 다음 정보를 봐야 합니다.

  • 각 컨테이너의 bind mount와 named volume
  • 호스트의 실제 절대 경로
  • 파일의 device와 inode
  • 수정 시각과 쓰기 주체
  • DB 변경 후 양쪽에서 즉시 같은 결과가 보이는지

2. 정적 배포에서 발견한 혼합 원본 문제

초기 배포 스크립트는 URL 목록을 OpenHands 로컬 SQLite에서 만들고 실제 HTML은 Oracle Ghost HTTP 서버에서 내려받는 구조였습니다.

OpenHands 로컬 DB → 발행된 slug 목록
Oracle Ghost HTTP → 각 slug의 HTML과 이미지

두 데이터가 같을 때는 잘 동작합니다. 그러나 Oracle Ghost Admin에서 새 글을 발행하고 OpenHands DB가 갱신되지 않으면 새 slug가 export 목록에 들어오지 않습니다. 반대로 OpenHands DB에만 존재하는 글은 Oracle Ghost에서 404가 발생합니다.

이 문제는 전형적인 “두 개의 진실” 문제입니다. 동기화 스크립트를 더 추가하기 전에 어느 시스템을 단일 원본으로 삼을지 정해야 합니다.

3. 콘텐츠 원본은 Oracle Ghost

현재 구조에서는 Oracle Ghost를 콘텐츠의 Single Source of Truth로 삼는 것이 가장 단순합니다.

OpenHands 또는 OpenCode
        ↓ Ghost Admin API
Oracle Ghost DB
        ↓ sitemap / Content API / public HTTP
정적 export
        ↓
GitHub Pages

OpenHands에서 글을 작성하더라도 로컬 SQLite를 직접 수정하지 않고 Ghost Admin API로 전송합니다. 이렇게 하면 작성자 관계, 태그, 발행 상태, 업데이트 충돌 처리를 Ghost가 담당합니다. DB 파일에 직접 행을 넣다가 posts_authors 관계를 빠뜨리는 문제도 피할 수 있습니다.

4. 배포 URL도 Ghost에서 가져와야 한다

정적 export의 글 목록은 로컬 DB가 아니라 Oracle Ghost의 sitemap이나 API에서 가져오는 편이 안전합니다.

  • /sitemap.xml: 공개된 전체 sitemap 인덱스
  • /sitemap-posts.xml: 공개 게시물
  • /sitemap-pages.xml: 공개 페이지
  • author/tag sitemap: 아카이브 페이지

이 구조에서는 Ghost Admin에서 발행된 내용이 곧 export 대상입니다. OpenHands 로컬 DB가 오래되어도 새 글이 누락되지 않습니다.

5. 코드와 콘텐츠는 다른 방식으로 동기화한다

모든 것을 하나의 공유 볼륨으로 해결할 필요는 없습니다. 데이터 성격에 따라 원본을 나누는 편이 좋습니다.

대상권장 원본전달 방법
글·태그·작성자Oracle GhostGhost Admin API
이미지Oracle Ghost contentAdmin API 업로드 또는 관리된 content 볼륨
테마·배포 코드Git 저장소commit, PR, pull/deploy
정적 사이트Ghost 공개 URL에서 생성deploy.sh → GitHub Pages

특히 SQLite 파일을 양방향 rsync로 맞추는 방식은 피해야 합니다. 실행 중인 DB를 통째로 복사하면 WAL 상태나 동시 쓰기 때문에 손상될 수 있고, 어느 변경을 유지할지 판단하기도 어렵습니다.

6. 검증 체크리스트

  1. Oracle Ghost DB의 PRAGMA integrity_check가 ok인지 확인합니다.
  2. 공개 post slug와 실제 HTTP 200 페이지를 대조합니다.
  3. 대표 이미지와 srcset URL의 응답 상태를 검사합니다.
  4. deploy 스크립트가 sitemap을 기준으로 URL을 생성하는지 확인합니다.
  5. OpenHands 로컬 DB를 발행 원본으로 사용하지 않는지 확인합니다.
  6. 코드는 Git, 콘텐츠는 Ghost라는 경계를 문서화합니다.

7. 오늘의 결론

동기화 문제를 해결하는 가장 좋은 방법은 동기화를 늘리는 것이 아니라 원본을 하나로 줄이는 것입니다. Ghost 콘텐츠는 Oracle Ghost에 쓰고, OpenHands와 OpenCode는 API를 통해 작업하며, 정적 배포도 Ghost가 공개한 sitemap을 기준으로 실행해야 합니다.
