[OpenHands 실전 5화] Ghost를 OpenHands 컨테이너에서 분리한 이유

OpenHands 재시작 때마다 Ghost가 멈춘 원인을 추적하고, 블로그를 독립 Docker 컨테이너로 분리한 기준과 운영 구조를 정리합니다.

Noah Sim

11 Oct 2026 — 5 min read
Share

오늘 작업은 단순한 프로세스 재시작 문제에서 시작했습니다. https://shining-sakaeru.github.io로 접속하던 Ghost가 OpenHands 컨테이너를 다시 만든 뒤 응답하지 않았습니다. 처음에는 Ghost만 다시 실행하면 끝날 문제처럼 보였지만, 원인을 따라가 보니 애플리케이션의 생명주기를 잘못 묶어 둔 구조가 핵심이었습니다.

1. 왜 Ghost 프로세스가 사라졌을까?

기존 Ghost는 OpenHands 컨테이너 안에서 다음과 비슷한 명령으로 실행되고 있었습니다.

nohup node versions/6.67.0/index.js > ghost.log 2>&1 &

이 방식은 Node 프로세스가 실행되는 동안에는 정상입니다. 하지만 Docker 컨테이너를 재생성하면 그 안의 모든 프로세스가 함께 종료됩니다. 호스트에 데이터 볼륨을 연결해 두었더라도 프로세스 자체는 보존되지 않습니다. 더구나 시작 스크립트가 컨테이너 엔트리포인트에 연결되어 있지 않다면 새 컨테이너가 올라와도 Ghost는 자동으로 시작되지 않습니다.

프로세스가 죽었을 때 다시 실행하는 watchdog도 만들어 보았습니다. 5초마다 127.0.0.1:2368을 확인하고 응답이 없으면 Ghost를 시작하는 구조였습니다. 실제로 Node 프로세스를 강제 종료했을 때 자동 복구되는 것도 확인했습니다. 그러나 컨테이너 자체가 내려가면 watchdog도 같이 사라집니다. watchdog은 프로세스 장애에는 효과가 있지만 컨테이너 생명주기 문제를 해결하지는 못합니다.

2. Ghost를 별도 컨테이너로 분리한 기준

Ghost는 글, 이미지, 테마와 SQLite 데이터베이스를 장기간 보존해야 하는 서비스입니다. 반면 OpenHands는 모델 설정이나 볼륨 구성을 바꾸며 비교적 자주 재생성할 수 있는 개발 도구입니다. 변경 주기가 다른 두 서비스를 한 컨테이너에 넣으면 한쪽의 유지보수가 다른 쪽의 장애로 이어집니다.

그래서 Oracle Linux 호스트에 Ghost 전용 Docker Compose 서비스를 만들었습니다.

services:
  ghost:
    image: ghost:6.67.0-alpine
    restart: unless-stopped
    ports:
      - "2368:2368"
    volumes:
      - ./content:/var/lib/ghost/content
      - ./config.production.json:/var/lib/ghost/config.production.json:ro

여기서 핵심은 세 가지입니다.

  • 독립된 생명주기: OpenHands를 재시작하거나 교체해도 Ghost는 계속 실행됩니다.
  • 영속 데이터: DB, 이미지, 테마를 호스트의 content/에 보존합니다.
  • 재시작 정책: restart: unless-stopped로 비정상 종료와 호스트 재부팅 후 복구를 Docker에 맡깁니다.

3. 운영 서비스와 개발 도구를 분리하면 달라지는 점

분리 전에는 OpenHands 설정을 고칠 때마다 Ghost 접속 여부를 함께 걱정해야 했습니다. 분리 후에는 각각 독립적으로 다룰 수 있습니다.

docker compose restart ghost
# 또는 OpenHands만 별도로 재생성

로그와 장애 범위도 명확해집니다. Ghost 문제는 Ghost 컨테이너 로그에서, OpenHands 문제는 Agent 환경에서 확인하면 됩니다. 포트 충돌이나 중복 Ghost 프로세스도 줄어듭니다.

4. 분리 과정에서 지켜야 할 데이터 원칙

컨테이너 분리보다 중요한 것은 기존 데이터 보존입니다. 전환 전에는 반드시 content/data/ghost-local.db, content/images/, content/themes/를 백업해야 합니다. SQLite DB를 사용하는 두 Ghost 프로세스를 동시에 띄워 같은 파일에 쓰게 해서도 안 됩니다.

안전한 전환 순서는 다음과 같습니다.

  1. 기존 DB와 content 전체를 백업합니다.
  2. 기존 Ghost 프로세스를 확인하고 중지합니다.
  3. 새 컨테이너에 content를 읽기·쓰기 마운트합니다.
  4. PRAGMA integrity_check와 기존 글·이미지를 확인합니다.
  5. 홈, 관리자 화면, 주요 글에 HTTP 200이 반환되는지 확인합니다.
  6. 컨테이너 재시작 후에도 정상 복구되는지 시험합니다.

5. 오늘의 결론

운영 서비스는 개발 도구의 편의 기능으로 띄우기보다 독립된 서비스로 관리하는 편이 안전합니다. watchdog은 보조 수단이고, Docker 환경에서는 컨테이너 분리·영속 볼륨·재시작 정책이 먼저입니다.
